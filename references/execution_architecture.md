# 创作执行架构

Muse 的知识来源只有两个引擎：[AI 基础审美推理](aesthetic_intelligence.md) 与 [用户品味记忆](taste_memory.md)。执行时再将两者共同形成的审美假设交给领域适配器、执行器和 Judge；下面的“四层职责”描述执行过程，不是新增的审美资产层。Muse 自身应能指导层级、构图、排版、色彩和交互选择，不以转交其他 skill 代替设计；不复制 CSS、动画库或某个工具的完整实现教程。

## 四层职责

| 层 | 负责 | 不负责 |
|---|---|---|
| Muse Core | 作品类型、受众与任务、内容账本、审美假设、个人品味和跨媒介关系 | 宣告最终的美，或收纳某一媒介的实现教程 |
| 领域适配器 | 把 Core 契约转换为当前媒介的执行上下文，筛选适用能力并收集结果 | 把 UI 规则扩散到文字、图像或演示 |
| 执行器 | 把上下文落实为代码、文字、图像或演示，处理媒介专有工艺 | 自行补造事实、改变任务、把默认风格当用户偏好 |
| Judge | 对照 brief、原材料和成品，分别观察审美力量、设计适切、伦理完整、个人共鸣及媒介表现 | 用创作者解释代替实际观察，或用 AI 自评冒充人的感受 |

同一个 Agent 可以承担多层，但交接记录和验收顺序仍分开；完整新作和高影响交付优先使用独立观察者。

流程为：`Muse Core → 当前媒介适配器 → 执行器 → Judge → 必要时返回对应层修正`。按当前产物选择所需适配器，各媒介规则保持边界；跨媒介任务可加载多个适配器，单独的文章任务不会加载前端能力。

## 执行器选择

按以下顺序选择，不为调用 skill 而替换成立的项目体系：

1. 用户指定的工具、格式或执行器。
2. 现有项目的设计系统、组件库、写作规范或制作流程。
3. 与媒介匹配的专门能力，例如 UI 的 `frontend-design`、演示工具或图像模型。
4. 宿主已有的通用创作能力。

专门执行器不存在时，用宿主已有能力落实 Muse 的设计选择；只有缺少实际制作工具时才说明无法交付的部分，不因缺少另一项 skill 而停在建议。执行器可用时按需读取，不把其整套规则复制进 Muse。

## 交接输入

Muse 将 [作品契约](artifact_contract.md) 压缩为执行器能直接使用的输入：

- `artifact`：作品类型、载体和交付格式。
- `audience_and_context`：受众、环境、使用频率与注意力条件。
- `primary_outcome`：主要动作或必须理解的主张，含关键路径。
- `content_ledger`：provided、verified、derived、placeholder/demo、unknown。
- `expression`：由内容产生的概念、品牌边界、已确认偏好及需要保留的识别线索。
- `required_states`：必须工作的状态、交互、运动职责和静态替代。
- `viewing_conditions`：目标尺寸、输入方式、导出或呈现环境。
- `constraints`：技术、性能、无障碍、时间和范围限制。
- `acceptance_evidence`：必须实际渲染、操作或核对的项目。

已有执行器要求 Design Context 时，以上输入直接满足上下文，不重复让用户填写。缺少但不阻断核心方向的信息保持 provisional 或 unknown；执行器不得为了页面完整自行具体化。

UI 任务还可按需附加执行器无关的 `design_state`：目标类型、baseline（可为 none）、active direction、branches、versions、[Context Manifest](toolkit/ui_project_context.md) 和已观察证据。状态恢复与迭代方式遵循 [UI 迭代协议](toolkit/ui_iteration_protocol.md)；资产按 [UI 资产协议](toolkit/ui_asset_protocol.md) 标明 reference、brand、content 或 placeholder/demo。任何画布、模型或 CLI 只是可替换执行器，不进入 Muse Core 的审美知识。

## 媒介适配接口

Muse 只保留各媒介需要交给执行器的差异，不收纳实现百科：

| 媒介 | 交给执行器的重点 |
|---|---|
| UI／网站 | 使用 [UI 适配器](toolkit/ui_adapter.md)：信息关系、真实文案、组件职责、关键状态、响应式语义、运动职责、目标尺寸 |
| 文字 | 使用 [文字适配器](toolkit/text_narrative_tool.md)：先出 WRITING.md 契约、媒介受众心智、深层架构模型、语言文风设定、事实与限定、段落推进与 24 种微创去油；作者声音来自当前样本或个人库中适用的 `author_voice` |
| 演示 | 使用 [演示适配器](toolkit/presentation_tool.md)：Muse 负责内容发现、视觉方向与平庸淘汰；专业演示执行器负责结构化制作、备注、导出、回读和文件验证 |
| 图像 | 使用[图像工作流](toolkit/image_visual_tool.md)：模式、逐张职责、最终提示词、实际参考及用途、保留／变化／区域、父版本、输出规格与验收条件；信息结构、表现语言和配色分别决定。需要画风参考时按需读[生图风格库](image_styles.md)，交接本次所用特征与调整，不要求执行器读取外部 skill |
| 动效／微交互 | 使用 [动效规范](toolkit/motion_tool.md)：物理阻尼、时长、状态转换、无障碍降级与 GPU 加速约束 |

具体字体组合、色彩函数、CSS 布局、组件 API、动画曲线、渲染参数等由执行器根据项目和媒介决定。Muse 可以评审这些选择是否服务契约，但不维护它们的完整教程。

## 执行器输出

执行器完成后返回：

- 成品或修改文件及运行方式。
- 使用了哪些给定内容，哪些仍为 unknown 或 demo。
- 影响主要任务的实现决定与代价。
- 已生成的渲染、交互或播放证据。
- 未实现、未观察和需要外部条件的范围。
- UI 任务返回本次采用的 direct edit／replace／branch／revert、父方向与版本、实际使用的上下文和资产，以及是否产生需要用户选择的分支。
- 图像任务逐张返回实际输出、可获得的工具／模型与参数、参考输入、任务状态、尝试与版本关系；成功项和失败项分开。生成状态与验收结论分开，未知的模型或服务端状态不能猜填。

“代码存在”“class 已添加”“没有控制台错误”只能作为实现信息，不能直接填写为体验通过。

## Muse 收口

Muse 收到成品后先对账，再按 [成品验收](acceptance_protocol.md) 观察。执行器的自评只是输入；阻断项由成品证据决定。若问题来自作品契约或表达概念，回到 Muse 层修正；若问题来自排版、组件、动画或响应式实现，把可观察现象和目标传回执行器，不在 Muse 中增加一次性实现补丁。

当多个执行器参与同一品牌时，共享核心主张、事实、语气和识别线索，各自保留媒介合适的结构和节奏。
